# M9 — Fidelity ladder and deployment shim

**Goal.** One scenario runs at every tier, so the sim-to-real gap becomes a measurement
instead of an assumption. Then point the same harness at real SCION.

**Depends on.** Everything. **Blocked by.** Hardware access (open question Q4).
**Size.** Large, and partly out of our control.

---

## Deliverables

### 1. Validate the tier adapters

Each currently a stub with an inferred mapping. `docs/ADAPTERS.md` holds the per-tier
checklist. Nothing here is trustworthy until its checklist is done, and no tier-0/2/3
number may be published before then.

**Tier 0 — ScionPathML.** Validate the column mapping against a real export. Critical
question: does the toolkit write `0` or an empty field for a missing measurement? If `0`,
probe R3 is untestable at tier 0 and we must say so rather than silently mapping zeros to
`None`. Also use these traces to **calibrate the tier-1 link model**, which is the main
value of tier 0 and is worth more than replay.

**Tier 2 — scion-dqn-sim.** Pin a commit. Validate the topology JSON schema. Determine
whether their traffic model can be driven with a population of agents or whether we drive
it externally.

**Tier 3 — ietf-scion-testbed.** Read `linkd`'s actual REST surface and correct
`adapters/testbed.py`; everything there is inferred from a README. Determine whether ID-INT
traces and border-router metrics can be read as `Observation`s — if so, tier 3 gives real
telemetry under controlled perturbation, which is the strongest evidence this project can
produce.

### 2. Scenario portability

Implement `scenario_to_shapes`: one scenario, four tiers. This is the contribution. If a
scenario cannot be expressed at tier 3, either the scenario schema or the adapter is
wrong; fix it rather than special-casing.

### 3. Cross-tier validation

Run the same scenario at tiers 1, 2, 3 with the same model and compare. Where they
diverge, and by how much, **is a publishable result in itself** and the instrument the
architecture proposal called for under risk E8.

### 4. `deploy/` — the production shim

The same harness driving a real SCION deployment: real telemetry in, real advisories out,
safety clamps, kill switch, and the full trace. Read-only shadow mode first. **Do not
enable actuation against anything real without an explicit, separate review.**

---

## Acceptance criteria

- [ ] All three adapter checklists complete and ticked in `docs/ADAPTERS.md`
- [ ] One scenario runs at tiers 1, 2 and 3 with a documented divergence report
- [ ] Tier-1 link model calibrated against tier-0 traces, error reported
- [ ] `deploy/` runs in shadow mode against a real stack, producing a trace and no actions
- [ ] Kill switch tested
- [ ] Every stub docstring in `adapters/` either validated or still marked unvalidated

## Must not break

The honesty convention. An unvalidated adapter says so in its docstring and in
`ADAPTERS.md`, and no number derived from it is published.

## Notes

Q4 may make tier 3 impossible. If so, say so plainly, top the ladder out at tier 2, and
record the sim-to-real claim as untested rather than quietly dropping it. The SEED emulator
already vendored in the repo is the fallback and it is a weaker one, because shaping through
SEED is clumsier than through `linkd`.
