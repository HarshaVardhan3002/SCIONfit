# M1 — Substrate at realistic scale

**Goal.** A static-topology SCION world with correct cryptographic churn, a monotone link
model, and array-backed state that holds 2,000 ASes without falling over.

**Depends on.** M0. **Blocks.** M2–M9.
**Size.** Large. The most important milestone in the project.

---

## Deliverables

### 1. `core/topology.py` — the static graph

ASes, ISDs, interfaces, inter-AS links, business relationships. **Immutable after
construction.** Numpy arrays indexed by integer id; string identifiers live in a side
table used only at the exposure boundary.

Three generators:
- `synthetic(n_ases, n_isds, seed)` — parameterised, fast, for tests
- `from_caida(path)` — realistic AS-level structure, with the AS-relationship to
  SCION-core mapping documented as an assumption (ADR + `ASSUMPTION(Q5)`)
- `from_dqnsim(path)` — read a `scion_topology.json` from the tier-2 upstream

Scale tiers defined in one place and used by every test and benchmark:
`smoke(20) / dev(200) / realistic(2000) / stress(20000)`.

### 2. `core/segments.py` — beaconing, expiry, re-signing

**This is the milestone's centre of gravity. Get it right.**

- Path segments constructed over the static topology, up-segment / core-segment /
  down-segment, combined into end-to-end paths.
- Each segment carries: interface sequence, an expiry, and cryptographic material
  represented abstractly (a generation counter and a signature id — we do not do real
  crypto).
- Segments are re-beaconed on a configurable interval. A re-signed segment has the **same
  interface sequence** and **new material**.
- Every path exposes **both** identifiers:
  ```python
  structural_id  # stable hash of the ordered interface sequence
  segment_id  # changes on every re-signing
  ```
- `identity_policy: "structural" | "crypto_bound"` decides which one `path_id` aliases at
  the exposure boundary. Neither is the blessed default until Q1 is answered.
- Path availability can change through AS policy filtering without any topology change.

Path sets are **materialised lazily per (src, dst) scope** and cached with an eviction
policy. Nobody enumerates all paths.

### 3. `core/linkstate.py` — load to metrics

Monotone non-decreasing cost in offered load. Non-negotiable: R7 tests models against this
property, and if the substrate lacks it the probe is meaningless. Add a property test.

- BPR-style form with a queueing tail; exact form gets an ADR
- exogenous background traffic: diurnal, weekly, seeded, **not readable by the model**
- per-direction state (forward/reverse availability differ)
- composition: latency sums, bandwidth minimises, loss compounds
- calibration hooks so M9 can fit parameters against tier-0 traces

### 4. `core/clock.py` — event-driven time

Priority-queue event loop. Simulated wall-clock that advances independently of the model's
thinking time, so that invariant 3 ("the network does not wait") is structurally enforced
rather than remembered.

### 5. `core/scenario.py` — the portable scenario schema

**Design this before the adapters harden.** Portability across the four tiers is the
project's contribution and it dies if each tier grows its own format.

A scenario declares: topology source, duration, seed, host population, traffic profile,
identity policy, and a timeline of events (link degradation, AS policy change, outage,
demand surge, scheduled topology change). It must be expressible as `linkd` REST calls in
M9 — check that while designing, not after.

## Acceptance criteria

- [x] `realistic` topology (2,000 ASes / ~10,000 links) builds in < 10 s —
      8 ms; beaconing on top of it 91 ms
      (`tests/test_performance.py::test_realistic_topology_builds_within_budget`,
      `::test_realistic_beaconing_builds_within_budget`)
- [x] One substrate step over `realistic` in < 10 ms — 0.64 ms averaged over an hour of
      simulated time, re-beaconing rounds included
      (`::test_realistic_substrate_steps_within_budget`); a cold path query is 2.6 ms
      (`::test_realistic_path_query_fits_in_the_step_budget`)
- [x] Memory for `realistic` under 2 GB — topology arrays 0.5 MiB, peak well under
      (`::test_realistic_topology_fits_in_the_memory_budget`)
- [x] `stress` (20,000 ASes) builds and steps without error; timing recorded, not gated —
      topology builds in 0.12 s, the whole substrate in 1.0 s, and a step costs 7.3 ms
      (`::test_stress_topology_builds_at_all`, `::test_stress_substrate_steps_at_all`)
- [x] Same seed produces an identical trace hash across two processes —
      `::test_the_same_scenario_hashes_the_same_in_another_process` runs a scenario with
      degradation, policy filtering and a demand surge under two values of
      `PYTHONHASHSEED` and compares `Substrate.digest()`
- [x] Property test: cost is non-decreasing in offered load, over 10,000 random states —
      `test_linkstate.py::test_cost_is_non_decreasing_in_offered_load`, with latency, loss
      and available bandwidth each checked separately alongside it
- [x] Re-signing test: after a beacon refresh, `structural_id` is unchanged and
      `segment_id` differs, for a path whose interfaces did not change —
      `test_segments.py::test_resigning_keeps_structural_id_and_changes_segment_id`, and
      the same property through composition in `::test_resigning_changes_path_ids_the_same_way`
- [x] Physical topology is provably immutable outside a declared scheduled event —
      the arrays refuse writes and the dataclass refuses rebinding
      (`test_topology.py`, immutability section); `without_links()` is the declared event,
      and `test_segments.py::test_filtering_removes_paths_without_touching_the_topology`
      shows availability changing with the graph untouched
- [x] `benchmarks/baseline.json` populated; CI fails on a >15% regression —
      `benchmarks/run.py`, wired into CI. Comparisons are scaled by a per-run calibration
      workload so the gate survives being run on a machine other than the one that
      recorded the baseline; `tests/test_benchmarks.py` covers the comparison logic

## Must not break

Determinism. The `PathModel` protocol.

## Notes

The single biggest risk is building this at toy scale and discovering at M3 that it does
not hold 2,000 ASes. Write the `realistic`-tier performance test **first**, watch it fail,
then build until it passes. Do not defer it.

Do not simulate beaconing message by message. Abstract the process, model its
consequences: segments appear, expire, and are replaced.

## Progress

Deliverables 2, 3, 4 and 5 are in, and deliverable 1 is in apart from its two file-backed
generators. ADR 0005 covers identity and search, ADR 0006 the load-to-metrics form, ADR
0007 the scenario schema. Every acceptance criterion is ticked.

**Still open, and deliberately so: `from_caida` and `from_dqnsim`.** Both need data files
the repo does not have — a CAIDA AS-relationships dump and a `scion_topology.json` from
the tier-2 upstream — and neither blocks M2 or M3, which run on `synthetic`. The scenario
schema already carries `source: "caida" | "dqnsim"` and `TopologySpec.build` raises a
`NotImplementedError` naming this paragraph, so scenarios written now stay valid when the
loaders land. Two things to carry over when they do: the path-count band has to be
re-measured rather than assumed (see point 1 below), and the AS-relationship to
SCION-core mapping needs an ADR and an `ASSUMPTION(Q5)`.

Three things found while building deliverables 2 and 3 that the remaining work has to
carry:

1. **Path counts are a whole-substrate property.** The tier band (100–300 at `realistic`)
   is met by `SegmentStore.for_tier`, and it moved every time the generator's multi-homing
   changed. `from_caida` will change it again and the band has to be re-checked there
   rather than assumed to carry over.
2. **The search caps are scenario parameters.** Beam width, hop limits and per-scope path
   caps change measured path diversity, so two runs are not comparable unless the scenario
   records them. `core/scenario.py` has to serialise them.
3. **So are the congestion constants.** The six `BPRParams` fields and the background
   traffic seed move every latency number in a run. Same requirement: `core/scenario.py`
   serialises them or two runs described as identical are not.
