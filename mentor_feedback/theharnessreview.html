The Harness After v1.2

The repository has not changed. The specification has — and it moved toward the harness on strategy while moving away from it on vocabulary. Two of the repo's eight open questions can be closed today.

A re-review with one side frozen is really a review of the moving side's consequences. Everything below follows from what v1.1 and v1.2 changed; where the first review's findings still stand unaltered, they are listed and not re-argued.

Verdict

The specification has converged on the harness's founding thesis. v1.2's §1 now argues that the value of a path oracle lies in improving a selection decision, not a number, and §28 insists decision quality be measured separately from accuracy. That is almost verbatim docs/DESIGN.md §1 — "existing SCION benchmarks answer is your prediction accurate; scionfit answers does your model survive being deployed alongside other copies of itself". The disagreement that made the first review's F4 uncomfortable has narrowed.

And the spec now names two milestones the harness is the natural rig for. M4½ is a closed-loop campaign over five axes — population, defector fraction, mechanism ladder, paths-per-selector, staleness. ADR-04 is now a slot requiring a four-way bake-off behind one interface. The harness is the only thing in either project that can run either. It has gone from "a useful evaluation tool" to "the instrument two spec milestones are specified in terms of", and neither document says so.

But v1.2 grew a vocabulary the contract cannot express. exposure/contracts.py contains zero occurrences of unit, tier, coverage, diversity or ambiguity. §7.1 now defines the unit as a computable object — the identifiable partition of the observed incidence matrix — and a spec-conformant model predicts unit states. PathModel.predict returns a mapping keyed by path. The gap the first review called F6 has hardened from "a missing field" into "a missing abstraction".

One substrate constant is wrong by 60×, and it happens to be the one the harness's headline experiment is built on.

Part one

What the audits handed the harness

The implementation audit that produced v1.1 answered questions the harness has been carrying as blockers. docs/OPEN_QUESTIONS.md still lists all eight as OPEN.

A1

Q1 is answered, and it changes what probe R4 is for

Closable

Q1 — "Is the SCION path fingerprint stable across re-signing?" — is marked OPEN · blocks M1, M5. It is answered. snet.Fingerprint is a SHA-256 over the ordered sequence of (ISD-AS, interface-ID) pairs and contains no cryptographic material whatsoever; the path combinator additionally collapses multiple constructions of the same interface sequence by default, exposing distinct segment IDs and MACs only to a caller who explicitly asks. The fingerprint is structural. It survives re-beaconing by design.

The repo anticipated exactly this branch: "If it does not change, the risk is hypothetical and R4 becomes a robustness check rather than a defect detector." That is now the situation, and M5's planned R4 needs re-aiming rather than merely re-implementing. As specified, M5's R4 fails a model that collapses under crypto_bound — but crypto_bound has no correspondent in the deployed stack, so such a model is not wrong about deployment, and a FAIL verdict would be a false positive against the thing conformance claims to measure.

What R4 should test instead. The deployment hazard is not the fingerprint; it is a model keying memory on something that is not the fingerprint — the raw path bytes, the dataplane path object, or the segment IDs that findAllIdentical=true exposes. So: keep both identity policies (they are cheap and the substrate already supports them), rename the failure semantics, and score the delta as a hygiene grade rather than a conformance failure. The probe becomes "does this model key on the identifier the protocol designates" — which is checkable, useful, and honest about severity.

This is the payoff the repo hoped for from the mentor question, arriving from the source tree instead. Q1 should be marked RESOLVED with the evidence, and identity_policy should acquire a documented default — structural, because that is what the stack does.

A2

Q6 is answered, and the answer invalidates a hardcoded constant

Closable

Q6 asks what SCMP rate limit border routers apply, noting it "sets the tool cost model. If probing is far cheaper or dearer than assumed, every budget-related result shifts." The answer: the SCMP specification says only that SCMP "may be subject to rate limiting", and there is no rate limiter in the router — no token bucket anywhere in the tree.

exposure/tools.py — an invented constant, now known to be invented
SCMP_LIMIT = RateLimit(calls=5, per_s=1.0)     # not a protocol constant
BWTEST_LIMIT = RateLimit(calls=1, per_s=30.0)
PATH_SERVER_LIMIT = RateLimit(calls=2, per_s=1.0)

This does not mean the limits should be removed — an unlimited probe budget is not a safe assumption either, and v1.2's §29 now carries the probe budget as a measured M0 parameter precisely because it is per-deployment and may be zero. What it means for the harness is narrower and more useful: the rate limits are a scenario parameter, not a substrate constant. They belong in Scenario alongside BeaconPolicy and LinkParams, so a run can state which regime it assumed, and so the M6 benchmark can sweep it rather than bake it in. Right now two runs under different real-world assumptions are indistinguishable in the report.

Mark Q6 RESOLVED — per-deployment, unspecified upstream, must be swept, and move the three constants into the scenario schema with the current values as defaults.

A3

Q2 has a sharper provisional answer than "open"

Partially closable

Q2 asks whether per-link offered load is observable or estimable, and warns that if not, "the response model conditions on a latent proxy instead and probes R6 and R7 need redesigning." The current answer, from the protocol rather than from a mentor: not directly observable — beacon metadata carries only static capacity, and the data plane exposes no per-hop state to endpoints — but estimable, and v1.2's §7.1 now says exactly under what condition: a unit's state is identifiable iff its column in the observed path-incidence matrix is distinguishable from its neighbours'.

So R6 and R7 do not need redesigning, but they do need re-reading. They test whether a model conditions on demand by handing it a demand vector. That is legitimate — a deployed oracle knows its own published shares — but it is a narrower claim than the probes' names imply, and it interacts with A6 below.

Part two

New defects and gaps

B1

The beacon interval is wrong by sixty-fold, in the constant the headline experiment rests on

Critical
core/segments.py — BeaconPolicy defaults vs. upstream
interval_s: float = 300.0      upstream default: 5 s   (60x)
lifetime_s: float = 21_600.0   upstream default: 6 h   (correct)

The lifetime is right — DefaultMaxExpTime = 63 gives 64 × 337.5 s = exactly 6 h, and the comment saying so is accurate. The interval is not: origination, propagation and registration all default to 5 seconds upstream, not 300. The ASSUMPTION(Q1) marker on BeaconPolicy correctly flags the numbers as unverified, so this is the marker working — but it has now been checked and should be corrected rather than left flagged.

Why this one matters more than an ordinary constant error. It is the clock of the identity-amnesia experiment. Under crypto_bound at a 300 s interval, a path's identifier changes about twelve times an hour and a model has real time to accumulate per-path state between refreshes. At the true 5 s interval it changes 720 times an hour, and the re-beaconing-to-lifetime ratio is roughly 4,300:1 rather than 72:1. A model keyed on a churning identifier would not degrade gracefully; it would hold essentially no state at all. The harness's demonstrated result — 21 distinct identifiers and stale_weight = 1.0 per refresh over 6,000 s — was measured at the wrong cadence and understates the effect by more than an order of magnitude.

Correcting it does not weaken the experiment; it makes it far more vivid, and it changes the M5 R4 design, because with A1's finding the interesting comparison is no longer structural vs crypto_bound but how fast can identity churn before a model that keys correctly still loses. That is a better probe and the substrate can already run it.

Fix: interval_s = 5.0 as the default, keep 300 available as a scenario override, and re-record the docs/evidence/ runs. Also worth adding: the 337.5 s expiry quantum is now a known constant and the substrate's continuous expiry_s should be quantised to it, since a model reasoning about time-to-expiry in a real deployment sees 256 discrete values, not a float.

B2

§7.1 gives units a computable definition, and the contract has no place to put one

Major

The first review's F6 said the contract had nowhere to put honest uncertainty. v1.2 hardened that from a missing field into a missing abstraction. §7.1 now defines the unit precisely — merge elements whose columns in the observed incidence matrix are identical — and §8 derives the ambiguity class from the same structure. A model built to this specification predicts unit states and composes them into path predictions through the §10 operator.

grep over the module every model imports
$ grep -c "unit\|tier\|coverage\|diversity\|ambiguity" \
      src/scionarena/exposure/contracts.py
0

PathModel.predict returns Mapping[path_id, Prediction]. There is no way for a model to say "here are my unit estimates, compose them yourself", and therefore no way for the harness to check whether a model's path predictions are consistent with any unit-level state — which is the single most characteristic property of a spec-conformant oracle, and the property probe R2 (composition onto an unseen path) is groping toward without being able to name.

This is now the harness's largest structural gap, and also its largest opportunity. R2 currently checks that a model produces a number for an unseen path and compares it to ground truth. With a unit-level output it could check something far stronger and much closer to what deployment needs: that the model's unit estimates, composed, reproduce its own path predictions — internal consistency — and that units shared between paths move together. Adding an optional units return alongside paths is backward-compatible (a model that omits it gets DECLARED_ABSENT) and it is what makes the harness able to test the spec's central abstraction rather than its surface.

B3

The contract conflates published intent with realised load — in a place the harness elsewhere gets right

Major

Demand is documented as "offered load as a fraction of total traffic for a scope" and is constructed from the published advisory:

exposure/session.py — Demand is built from intent
def demand_from_advisory(advisory: Advisory, n_hosts: int = 1) -> Demand:
    """Contract-shaped demand from a published advisory. Used by M3."""
    return Demand(per_path=dict(advisory.normalised()), n_hosts=n_hosts)

Meanwhile the telemetry stream reports realised share and its docstring is emphatic about the distinction: "share is the realised share, not the published weight. The two differ by the sampling noise, and a model that assumes its advice was followed exactly is wrong by exactly that much."

The harness knows this in one file and forgets it in the other. A model handed Demand is handed its own intent labelled as load — precisely the assumption streams.py warns is wrong. v1.2 makes this sharper still: §19.6's performativity diagnostic and ADR-15's graduation path both turn on the gap between what was published and what happened, and the partially-performative framing v1.2 adopts makes the responsive fraction the quantity to estimate. A contract that hands the model a demand vector indistinguishable from its own advisory cannot test whether the model estimates that fraction, or even whether it knows the two differ.

Fix: split the field — Demand.intended and Demand.realised, with realised populated from hosts.shares() and legitimately None where no telemetry covers the path. That single change makes R6 sharper, makes R9 (self-consistency) test something stronger, and creates the hook for a performativity probe that does not otherwise exist.

B4

v1.2's per-class layer rules are directly probeable, and define a failure the harness cannot currently see

New probe

§20.6 now states which layers each requirement class may rank on and which may only widen intervals — latency class ranks on static plus liveness and widens on dynamic; throughput ranks on dynamic; compliance ranks on static attributes alone, fail-closed. The reasoning is a timescale argument: ranking on a 15-second-old congestion estimate is routing on lagged load, which is the documented oscillation mechanism.

This creates a model failure the harness has no probe for and could detect cleanly. Hold the static layer fixed, vary only the dynamic layer, and ask a latency-class model for a ranking. If the ranking reorders, the model is ranking on the layer §20.6 forbids. That is a one-variable behavioural probe of exactly the kind docs/DESIGN.md §5 argues for, it needs no new substrate, and it catches a defect that currently reaches the closed-loop tier undetected — where it shows up as oscillation and gets attributed to the model's advisory shape rather than to its metric choice.

Call it R11. It pairs naturally with R7 (monotone in load), which establishes the model can see the dynamic layer; R11 then establishes it uses it in the right place.

B5

Calibration is now specified precisely enough to probe, and the update rule is three lines

New probe

The first review's F5 said nothing tests calibration. v1.2 removed the excuse: §19.5 now specifies the exact online update — α_{t+1} = α_t + η (target − 1{y_t ∈ C_t}) — and N4 claims long-run coverage on arbitrary sequences rather than monitored-under-shift.

Two things follow for the harness. A coverage detector in instrument/ is now a small, well-defined object: run the event log, count interval hits against realised observations per bucket, report trailing coverage. It is already M4 deliverable 2 and it converts R5 from a shape check ("three ordered quantiles") into a test of the property that matters. And a calibration-under-shift probe becomes possible: apply a scheduled link_degrade, then measure whether the model's intervals recover nominal coverage and how fast. A model with fixed split-conformal intervals will not recover; one with an adaptive level will. That is a real discrimination between two model designs the spec now has an opinion about.

B6

The harness is M4½'s rig, and is two knobs short of running it

Opportunity

v1.2 created M4½: run the closed-loop campaign to the "+jittered mirror" rung before building coordination, and let the measured compliant-share threshold decide whether M5 happens. Its axes are population size, defector fraction, mechanism ladder, paths-per-selector, and staleness. Against the harness:

The discipline rung remains the highest-value work in the repository, and the seam is still where it was: HostParams.resample_s is a minimum dwell in all but name and _thin already carries placed hosts across rounds.

The paths-per-selector axis is new since the first review and is cheaper than it looks: a selector that picks one path is a population of size one sampling the advisory, so it is a constraint on the draw rather than a new mechanism.

One caveat on B1. The 5 s figure is the upstream default configuration, not a protocol constant — a deployment may configure otherwise, and the topology generator in a testbed often does. The correction is therefore to the default and to the comment that calls 300 s plausible, not to the existence of the knob. What is not defensible is leaving a value sixty times off the reference implementation as the number every committed evidence run was measured at.
